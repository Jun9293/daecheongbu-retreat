# 맥미니 이전 — 2단계 (맥용 실행 파일)

**여기까지는 작성과 로컬 검증입니다.** 터널 기동 · 실제 배포 · sudo 가 필요한 일은 안 했습니다.
**첫 배포는 처음부터 맥미니에 합니다**(8장 · 2026-10-01 사람이 정함) — 아직 실사용자에게 배포하기
전이라 윈도우에서 운영을 옮기는 것이 아닙니다. 지금까지 돌려 온 절차의 정본은 `docs/배포-안내.md`
(윈도우)이고, 실제 배포를 확인한 뒤에 CLAUDE.md 11장 · 11-2 와 함께 고칩니다.

## 6. 맥미니의 전원·로그인 상태 (2026-09-30 · sudo 없이 읽기만)

`pmset -g` · `pmset -g custom` · `fdesetup status` · `defaults read /Library/Preferences/com.apple.loginwindow autoLoginUser` 로 읽은 값입니다. **바꾸지 않았습니다** — 바꾸는 것은 sudo 나 시스템 설정 화면이 필요합니다.

| 무엇 | 읽은 값 | 뜻 |
|---|---|---|
| 잠자기 | `sleep 0` (AC) | 시스템이 잠들지 않는다 — 윈도우 안내서 7-1 에 해당하는 것은 이미 됐다 |
| 디스플레이 잠자기 | `displaysleep 10` | 화면만 꺼진다. 서버와 무관 |
| 정전 후 자동 시동 | `autorestartatconnect 1` · `autorestart 0` | **켜져 있는 것으로 읽힌다** — 아래 3단계 재확인 |
| 네트워크로 깨우기 | `womp 1` | 켜져 있다 |
| FileVault | 꺼짐 | 자동 로그인이 가능한 조건 |
| 자동 로그인 | 사용자가 정해져 있음 · `kcpassword` 있음 | 재부팅하면 로그인까지 스스로 간다 → **LaunchAgent 가 뜬다** |

**그래서 5장 첫 줄(LaunchAgent 는 로그인해야 뜬다)은 지금 설정으로 풀려 있습니다** — 자동 로그인이 켜져 있기 때문입니다.

**3단계 재확인 (2026-09-30)** — 시스템 설정 화면에는 「전원이 연결되면 시작: 항상」 으로
보입니다. `pmset -g cap` 이 이 기계가 받는 설정으로 **`autorestart` 와 `autorestartatconnect`
를 따로** 내고, 화면의 그 항목과 이름·값이 맞는 것은 **`autorestartatconnect 1`** 입니다 —
**화면과 일치합니다.** `autorestart 0` 은 그와 별개인 옛 「정전 후 재시동」 키로 보입니다.
**2단계에서 「꺼져 있다」 고 적은 것은 뒤의 값만 본 판단이었습니다.** 다만 이것은 이름과
화면으로 맞춘 것이고 **전원을 실제로 뽑아 보지는 않았습니다** — 리허설에서 한 번 뽑아 보고
스스로 서는지 봅니다(8-8).

> **대가** — FileVault 가 꺼져 있고 자동 로그인이 켜져 있으면 기계를 손에 넣은 사람은 디스크와 로그인된 세션을 그대로 얻습니다. `data/` 에 DB · 서명키 · VAPID 키 · API 키가 있습니다. 이 둘을 그대로 둘지는 사람이 정합니다.

## 7. seed.py 를 돌리지 않는 까닭과 빈 맥에서 처음 켤 때

**`serve.sh` 는 seed 를 부르지 않습니다.** 윈도우의 `run.bat` 은 `data\app.db` 가 없으면
`seed.py` 를 불렀는데, 그 길로 2026-08-29 에 개발 시드가 그때 하나뿐인 DB 에 들어가 그대로
운영이 됐습니다(CLAUDE.md 0장 둘째 예외 · 6-9). 그 뒤로 `seed.py` 는 **운영 폴더(`data/`)를
가리키면 스스로 멈춥니다**(`운영경로인가`). 운영 자료는 시드로 만드는 것이 아니라 **윈도우에서
옮겨 오는 것**이라, 앱을 띄우는 스크립트가 시드를 알 이유가 없습니다.

**빈 맥에서 처음 켜면** — 운영 자료를 안 옮기고 `serve.sh`(또는 launchd)로 띄우면 앱이
**빈 DB** 에 표를 만들고 서명키를 새로 씁니다(2단계 검증에서 실제로 그렇게 떴습니다).
계정이 없으니 `scripts/계정문열기.py --첫관리자` 로 첫 관리자를 만듭니다 — **비밀번호가 창에
찍히므로 사람이 돌립니다**(11-2). 절차는 `docs/배포-안내.md` 15-4 입니다.
연습용 자료는 `DCB_DATA_DIR` 을 운영 폴더 밖으로 두고서만 시드를 씁니다.

### 8-0. 전제 · 일정 · 정해진 것

**전제 — 운영을 옮기는 것이 아니라 첫 배포입니다** (2026-10-01 사람이 정함). 아직 실사용자에게

- 「대청부 앱」 은 시스템이 시작할 때 도는 작업이라 켜기만 해서는 안 뜹니다 — 그래서 한 번 시작시킵니다

**사람 몫** — 이 절 전부(관리자 권한 · 윈도우 · 암호 입력 · Drive 에 올리기).

### 8-5. 맥 — 새 터널을 만들고 DNS 를 돌린다

**자격증명은 새로 만듭니다**(12-5). 윈도우의 터널 자격증명 파일은 옮기지 않습니다 — 그래서
**두 기계가 같은 터널을 쥐는 일이 구조로 없습니다.** 바깥 주소는 DNS 가 가리키는 **한 터널**로만 갑니다.

**① 사람 — Cloudflare 로그인과 본인 확인.** 터미널에서 아래를 치면 브라우저가 열립니다.
로그인하고 본인 확인(2단계 인증)을 거친 뒤 도메인을 고릅니다. 이 창은 그 화면에 손대지 않습니다.

```bash
/opt/homebrew/bin/cloudflared tunnel login
```

**`cloudflared` 는 전체 경로로 칩니다** — 작업하는 창의 PATH 에 없습니다(12-17). 아래 명령도 같습니다.

**② Claude Code — 터널을 만들고 설정을 채운다.** 새 터널 이름은 그날 정합니다(옛 이름과 달라야 합니다).

```bash
/opt/homebrew/bin/cloudflared tunnel create <새 터널>
cp scripts/mac/cloudflared-config.template.yml ~/.cloudflared/config.yml
chmod 600 ~/.cloudflared/*.json ~/.cloudflared/config.yml
```

`~/.cloudflared/config.yml` 에서 **두 줄**을 고칩니다 — `tunnel:` 을 새 터널 이름으로(견본에는 `○○` 로
비어 있습니다), `credentials-file:` 을 방금 생긴 `.json` 의 경로로. **그 파일의 내용은 열어 보지도
찍지도 않습니다** — 경로만 적습니다.

**③ Claude Code — 터널을 올린다.** 먼저 `○○` 가 남았는지와 **`credentials-file` 이 가리키는 파일이 실제로 있는지** 봅니다(경로만 보고 내용은 열지 않습니다) — **첫 줄이 `멈춤` 이면 아래를 치지 않고 ② 로 돌아갑니다.**

```bash
c=~/.cloudflared/config.yml; f="$(sed -n 's/^credentials-file:[[:space:]]*//p' "$c" 2>/dev/null | head -1 | sed 's/[[:space:]]*$//')"; if [ ! -f "$c" ] || grep -q '○○' "$c" || [ -z "$f" ] || [ ! -f "$f" ]; then echo '멈춤 — 설정이 없거나, 안 채운 자리가 남았거나, 자격증명 파일이 그 경로에 없습니다'; else echo '채움'; fi
cp ~/dcb-plist/com.daecheongbu.tunnel.plist ~/Library/LaunchAgents/
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.daecheongbu.tunnel.plist
sleep 10
tail -5 data/launchd-tunnel.log
/opt/homebrew/bin/cloudflared tunnel info <새 터널>
pgrep -x cloudflared | wc -l
```

**이렇게 나오면 성공** — `tunnel info` 에 커넥터가 **하나** 보이고 마지막 줄(프로세스 수)이 `1` 입니다.
아직 바깥 주소는 옛 터널을 가리키므로 바깥에서는 안 열립니다 — 그것이 맞습니다.

**커넥터는 `tunnel info` 의 표에서 줄 수로 셉니다** — `CONNECTOR ID` 로 시작하는 머리 줄 아래의 줄 하나가
커넥터 하나입니다(2026-10-07 에 돌려 꼴을 봤습니다). 그 줄 끝의 `EDGE` 칸은 「가닥 수 x 자리」 를 쉼표로 이은
것이고 **앞의 수를 더한 것이 연결 가닥 수**입니다(그날 1 · 2 · 1 로 넷 · 12-17) — 커넥터 수가 아닙니다. **프로세스 수(`pgrep`)와 따로 셉니다** — 커넥터는
Cloudflare 가 본 수라 다른 기계에서 붙은 것까지 세고, 프로세스는 이 맥에서 도는 것만 셉니다.

**④ 사람이 「돌려」 한 뒤 — DNS 를 새 터널로.** 바깥으로 나가는 변경이라 사람이 그 자리에서 정합니다.

```bash
/opt/homebrew/bin/cloudflared tunnel route dns --overwrite-dns <새 터널> <바깥 주소>
```

**⑤ 사람 — 바깥에서 확인.** 휴대폰(**와이파이를 끄고 LTE**)으로 바깥 주소를 열어 로그인 화면이 뜨는지
봅니다 — 맥 안에서 열면 같은 집 안이라 바깥을 잰 것이 아닙니다. DNS 가 바뀌는 데 몇 분 걸릴 수
있습니다. **아직 쓰는 사람이 없으니 서두르지 않습니다** — 안 열리면 기다렸다 다시 봅니다.

**사람 몫** — ① 로그인 · 본인 확인 · 도메인 고르기 ④ DNS 를 돌려도 되는지 정하기 ⑤ 바깥 확인.
**Claude Code 몫** — ② ③ 과 ④ 의 명령(사람이 정한 뒤) · 로그와 커넥터 수 확인.

### 8-6. 옛 터널 정리 — 서두르지 않는다

**옛 터널 삭제는 귀국 뒤 리허설(8-8 · 10/27 이후)이 통과한 다음에 합니다** (2026-10-07 사람이 정함 · 12-21).
**그때까지 옛 터널은 윈도우로 돌아가는 길로 남습니다** — DNS 를 옛 터널로 되돌리고(12-18) 윈도우 터널을
다시 켜는 것(8-2-5)이 그 길이고, 터널을 지우면 닫힙니다.

**DNS 가 새 터널을 가리킨 뒤로 옛 터널은 아무 일도 하지 않습니다.** 윈도우의 터널 서비스는 8-2 에서
멈추고 시작 유형을 바꿔 두었으므로 재부팅해도 안 켜집니다. **쓰는 사람이 없으니 급히 지울 까닭이 없습니다.**

두 기계가 함께 받지 않게 하는 장치는 넷입니다 —
① 윈도우의 터널 서비스와 앱 작업은 **멈춘 데다 다시 켜지는 길까지 꺼져 있다**(8-2)
② 바깥 주소의 DNS 는 **한 터널만** 가리킨다(8-5 ④) — 옛 터널이 실수로 켜져도 주소는 그리로 안 간다
③ 맥의 새 터널은 커넥터가 **하나**다(8-5 ③)
④ 이 차례는 **한 사람이 이 장을 위에서부터** 따라간다

정리할 때(윈도우 · PowerShell 관리자) —

```
C:\cloudflared\cloudflared.exe tunnel list
C:\cloudflared\cloudflared.exe tunnel delete <옛 터널>
sc.exe delete Cloudflared
```

터널을 지우면 윈도우에 남은 그 자격증명 파일은 쓸모가 없어집니다. 그 파일을 지우는 것은 8-9 의
윈도우 원본 정리와 함께 합니다.

**사람 몫** — 이 절 전부(윈도우 · 관리자 권한 · Cloudflare 에 닿는 삭제).
**Claude Code 몫** — 맥에서 `/opt/homebrew/bin/cloudflared tunnel list` 로 옛 터널이 사라졌는지 읽기.

### 8-7. 되돌리기 — 맥에서 이전 판으로

**윈도우로 돌아가는 것은 이 절의 차례가 아닙니다** — 돌아갈 「운영」 이 없기 때문입니다. 다만 그 길을
닫지는 않았습니다: 옛 터널을 리허설 통과 때까지 남겨 둡니다(8-6 · 12-21 · 돌리는 법은 12-18). 되돌리는 것은
**맥 안에서 이전 판으로**입니다. 무엇이 잘못됐는지에 따라 셋 중 하나입니다.

**ㄱ. 코드를 이전 판으로** — 새 코드가 문제일 때. 자료는 건드리지 않습니다.

```bash
cd ~/Projects/대청부-수련회-시스템
git log --oneline -5
git switch --detach <성한 커밋>
lsof -nP -iTCP:8000 -sTCP:LISTEN -t
launchctl kickstart -k gui/$(id -u)/com.daecheongbu.app
sleep 5
lsof -nP -iTCP:8000 -sTCP:LISTEN -t
```

**이렇게 나오면 성공** — 두 PID 가 **다릅니다**(배포-안내 15-5 와 같은 판정).

**ㄴ. 자료를 이전 판으로** — DB 가 잘못됐을 때. 서버를 내리고 **같은 날짜의 셋을 함께** 되돌립니다
(CLAUDE.md 11-2 「되돌리기」). **이름이 가장 최근인 판이 성한 판은 아닙니다** — 먼저 빈 판이 있는지 봅니다.
지금 것은 지우지 않고 옆으로 치웁니다.

```bash
launchctl bootout gui/$(id -u)/com.daecheongbu.app
lsof -nP -iTCP:8000 -sTCP:LISTEN -t
.venv/bin/python scripts/backup.py --살핀다
ls data/backups/app-*.db | tail -5
d="data/되돌리기전-$(date +%Y%m%d-%H%M)"; mkdir -p "$d"
mv data/app.db data/uploads data/vapid_private.pem "$d/"
cp "data/backups/app-<때>.db" data/app.db
mkdir data/uploads && unzip -q "data/backups/uploads-<때>.zip" -d data/uploads
cp "data/backups/vapid-<때>.pem" data/vapid_private.pem && chmod 600 data/vapid_private.pem
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.daecheongbu.app.plist
sleep 5
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/healthz
```

**이렇게 나오면 성공** — 둘째 줄은 아무것도 안 나오고(서버가 내려감) 마지막 줄이 `200` 입니다.
그 날짜에 업로드 zip 이나 VAPID 사본이 없으면(올린 파일이 없던 날) 그 줄은 건너뛰고 치운 것을 되돌려 놓습니다.

**ㄷ. 바깥 문을 닫는다** — 무엇이 잘못됐는지 모를 때 먼저 하는 것. 터널만 내리고 **다시 켜지는 길**
(LaunchAgents 의 plist)까지 치웁니다. 앱과 자료는 그대로 두고 안에서 들여다봅니다.

```bash
launchctl bootout gui/$(id -u)/com.daecheongbu.tunnel
mkdir -p ~/dcb-plist/내림 && mv ~/Library/LaunchAgents/com.daecheongbu.tunnel.plist ~/dcb-plist/내림/
pgrep -x cloudflared
```

**이렇게 나오면 성공** — 마지막 줄이 아무것도 안 나옵니다. 바깥 주소는 오류 화면이 되는데,
쓰는 사람이 없는 동안에는 그것으로 잃는 것이 없습니다. DNS 는 손대지 않습니다.

**맨 처음으로** — 옮긴 자료 자체가 틀렸으면 8-2 부터 다시 합니다. 윈도우 원본이 정리되기 전(8-9)이라
가능한 길이고, **그래서 원본 정리를 서두르지 않습니다.**

**사람 몫** — 어느 판으로 돌아갈지 정하기(ㄴ 의 `<때>`) · 사용자에게 안내한 뒤라면 알리기.
**Claude Code 몫** — 미리 읽어 보이기(빈 판 · 최근 판 목록) → 사람이 정한 판으로 되돌리기 → 다시 재기.

## 9. 백업 위치를 바꿀 때 (`DCB_BACKUP_DIR`)

**지금은 쓰지 않는 차례입니다** — 백업 위치는 내장 `data/backups` 로 정해져 있습니다(12-4).
위치를 옮기게 될 때를 위해 남겨 둡니다.

**위치를 바꾸면 옛 판은 옛 자리(`data/backups`)에 그대로 남습니다** — 옮겨 주는 것이 없습니다.
그 안에는 **`지키는판`**(사고의 증거 · 문서가 되돌리는 자리로 가리키는 사본 — `scripts/backup.py`)도
있습니다. 그대로 두면 ① 새 자리의 정리(30판 · 10GB)는 옛 판을 모르고 ② 신선도 점검과 `--살핀다` 는
새 자리만 봅니다. ③ 설정 › 점검의 「백업 마지막」 과 자가진단의 백업 용량도 **새 자리를 봅니다** —
전에는 `data/backups` 를 박아 두고 읽었는데 2026-09-30 에 위치를 읽는 곳을 `app/paths.py` 의
`백업자리` 하나로 모았습니다. 운영 스크립트가 작업 직전에 뜨는 되돌림 사본은 옛 자리에 남습니다(12-4).

**옮기는 차례** — 백업이 돌지 않는 때(03:00 · 09:00 밖)에 합니다.

```bash
launchctl bootout gui/$(id -u)/com.daecheongbu.backup
launchctl bootout gui/$(id -u)/com.daecheongbu.backupcheck
rsync -aH data/backups/ "<새 자리>/"
ls data/backups/app-*.db | wc -l
ls "<새 자리>"/app-*.db | wc -l
```

- **`-H` 가 중요합니다** — 업로드 zip 은 하드링크로 이어져 있어서(4-9), 그냥 복사하면 판마다 실체로
  펼쳐져 크기가 몇 배가 됩니다. `cp -R` 은 이것을 지키지 않습니다
- 두 수가 같으면 `.env` 에 `DCB_BACKUP_DIR=<새 자리>` 를 적고 두 작업을 다시 로드한 뒤
  `scripts/mac/백업점검.sh` 로 「괜찮음」 을 봅니다
- **옛 자리는 지우지 않습니다** — 새 자리에서 한 번 이상 성한 판이 뜨고, 되돌리는 자리를 가리키는 문서가
  새 자리를 가리키게 고쳐질 때까지 둡니다. 지울지는 사람이 정합니다(0장)
- 새 자리가 외장 드라이브면 **빠진 날은 백업이 69 로 멈추고**, 신선도 점검이 30시간 뒤 알립니다

## 10. cloudflared 를 올린 뒤

`brew upgrade`(또는 `brew upgrade cloudflared`)는 **파일만 바꾸고 도는 터널은 옛 판 그대로** 둡니다 —
plist 가 부르는 `/opt/homebrew/bin/cloudflared` 는 새 판을 가리키게 되지만, 이미 떠 있는 프로세스는
옛 파일을 들고 있습니다. 그리고 plist 에 `--no-autoupdate` 가 있어 스스로도 안 바뀝니다.
**그래서 올린 뒤에는 터널을 다시 켭니다.** **언제 올리는지는 12-19 가 정합니다** — 리허설(8-8)을 통과한 뒤 따로이고,
올리기 전에 지금 실행 파일을 옆에 사본으로 떠 둡니다.

```bash
/opt/homebrew/bin/cloudflared --version
launchctl kickstart -k gui/$(id -u)/com.daecheongbu.tunnel
sleep 10
tail -5 data/launchd-tunnel.log
```

- **`brew upgrade` 는 이름을 안 줘도 cloudflared 를 올립니다** — 다른 것을 올리다 함께 바뀌므로 brew 를
  돌린 날은 이 차례를 한 번 봅니다
- 다시 켜는 동안 몇 초 바깥에서 안 열립니다 — 사람이 쓰지 않는 때에 합니다
- **`brew services start cloudflared` 는 쓰지 않습니다** — launchd 에 작업이 하나 더 서서 같은 터널을
  두 번 돌리게 됩니다(두 커넥터가 요청을 나눠 받는 사고 — 8-6 이 막으려는 것)

## 12. 확정된 결정 (2026-09-30 · 사람이 정함)

### 12-1. 백업 실패 · 신선도는 로그 한 줄만 둔다

### 12-2. Time Machine 대상 드라이브를 암호화했다 (2026-09-30)

- 11장에서 읽은 대로 대상 드라이브가 암호화되어 있지 않고 `data/`(DB · 키 파일)가 포함되어 있어
  **암호화하기로 정했고, 2026-09-30 에 끝냈습니다** — 대상을 **지우고 암호화 형식으로 새로 만들었고,
  첫 백업까지 끝났습니다**
- **이전 백업 이력은 새로 시작됐습니다** — 그 전의 Time Machine 스냅샷으로는 돌아갈 수 없습니다.
  되돌리는 자리는 여전히 `data/backups/` 의 앱 판입니다(11-2 「백업」)
- 암호를 정하고 넣는 일은 사람이 했습니다. **암호 · 힌트 · 키체인 내용은 저장소 · 보고 · 채팅
  어디에도 적지 않습니다**
- 2026-10-01 에 다시 읽은 값(읽기만): 설정 파일의 `LastKnownEncryptionState` 가 `Encrypted`, 볼륨은

  포함. 마운트 자리는 이름이 겹쳐 `/Volumes/Backup 1` 로 읽혔습니다(볼륨 이름은 그대로 `Backup`)

  드라이브가 열리고 다음 Time Machine 백업이 이어지는지**를 보는 것입니다(2026-10-01 정함)

### 12-3. tmutil 에 전체 디스크 접근 권한을 주지 않는다 — 정본 키는 `SnapshotDates` 의 마지막 값

  정했습니다** — 터미널 전체에 모든 파일을 읽을 권한을 여는 것이라, 날짜 하나를 읽으려고 열기에는 넓습니다
- Time Machine 의 마지막 백업 시각은 **설정 파일**(`/Library/Preferences/com.apple.TimeMachine`)의
  **`SnapshotDates` 의 마지막 값을 정본으로** 읽습니다(2026-10-01 정함). **`LastBackupActivity` 는 정본이
  아닙니다** — 2026-10-01 에 두 값이 하루 가까이 달랐습니다(앞의 것은 첫 백업을 시작한 때로 보입니다)
- **키가 없거나 값이 비면 「못 읽음」** 으로 적고 멈추지 않습니다 — 이 시각을 읽는 코드는 저장소에
  없고(2026-10-01 grep), 사람이나 이 창이 위의 키를 읽어 보고에 적을 때의 규칙입니다
- **대가** — 설정 파일의 날짜는 Time Machine 이 적어 둔 기록이라, 백업 파일이 실제로 드라이브에 성하게
  있는지까지는 말하지 않습니다

### 12-4. 백업 위치는 내장 `data/backups` 로 둔다 — 되돌림 사본도 그대로

### 12-9. 정리 로그 · 배포 뒤로 미룬 것 (2026-10-01)

**정리 로그는 지운 판의 이름을 남깁니다** — 지웠으면 「정리:」 한 줄이고 꼴은 아래와 같습니다
(2026-10-07 에 `data/launchd-backup.log` 와 글자로 견줬습니다). 지울 판이 없으면 그 줄을 안 냅니다.

    [날짜 시각] 백업:   정리: 지우기 전 38판 (지킬 판 7) → 지운 판 1 (파일 4개): 20260911-030002

- **「지우기 전 N판」 은 지키는 판까지 센 수**이고, **「지킬 판」 이 코드의 `지키는판`** 입니다(로그는 그 말로 적습니다)
- **이름은 판의 때(`YYYYmmdd-HHMMSS`)** 이지 파일 이름이 아닙니다 — 앞 10개까지이고 나머지는 「외 N판」
- **「파일 N개」 는 그 판에서 실제로 지운 파일 수**라 판마다 다릅니다. 한 판에 딸린 파일은 많아야 넷입니다
  (`backup.files_of` — DB · VAPID 사본 · 업로드 zip · 행 수 옆 파일). **새벽 백업(`run`)이 뜬 판은 넷**이고,
  **운영 스크립트가 작업 직전에 뜬 사본(`snapshot` 만 부른 판)은 DB 와 행 수 옆 파일 둘**입니다 — 코드로 확인한 규칙이고
  닷새치 로그(넷 · 둘 · 둘 · 둘 · 넷)와 맞습니다. VAPID 키나 올린 파일이 없던 날의 새벽 판은 넷보다 적습니다
- 같은 묶음의 맨 끝 줄은 2026-10-07 까지 한 수만 적어, 지키는 판까지 센 그 수가 한도 30 을 넘은 것처럼
  읽혔습니다. 같은 날 문구를 고쳐 **다음 백업부터** 「보관 중 N개 (지키는 판 A + 그 밖 B · 성한 판은 최대 30개)」
  로 나옵니다 — 세는 것과 지우는 것은 그대로입니다. 「그 밖」 이라고 적는 것은 의심 판도 거기 들 수 있어서입니다
