## 4. [7] 닫혀야 하는데 안 닫히는 길 — 그리고 [막1] 을 고친 것

`downAt` 이 `click` 캡처에서만 비워져서, **`click` 없이 끝난 포인터**
(우클릭 · `pointercancel` · 창 밖에서 뗀 드래그) 뒤에 남았습니다.
그러면 **`pointerdown` 이 없는 클릭**(키보드: 포커스 + 엔터)이 옛 값을
써서 닫히지 않습니다.

### 2판은 이것을 시간으로 갈랐고, 그게 「막아야 함」 이 됐습니다

`기록수명 = 1500` 을 두고 **`pointerdown` 부터** 쟀습니다. 그러면 그것은
「기록이 남아 있는 시간」 이 아니라 **드래그 길이의 상한**이 됩니다 —
**1.5초를 넘게 끌면 이번에 고친 고장이 그대로 납니다.** 글자를 끌어
선택하는 것은 흔히 그보다 길고, 그건 `pointer` 로 듣는 근거로 제가 든
바로 그 동작입니다.

**걷어낸 400ms 창은 `mouseup` 부터 재던 것이라 드래그가 아무리 길어도
걸리지 않았습니다** — 그 자리에서는 옛것보다 나빠진 셈이었습니다.

브라우저에서 실제로 쟀습니다.

| | 1500ms 판 | 지금 |
|---|---|---|
| 빠른 드래그 (0ms) | 안 닫힘 | 안 닫힘 |
| **느린 드래그 (2초)** | **닫힘 ✗** | 안 닫힘 ✓ |
| 아주 느린 (5초) | — | 안 닫힘 ✓ |
| 여백 클릭 | — | 닫힘 ✓ |
| 우클릭 뒤 키보드 클릭 | — | 닫힘 ✓ |

### 시간 대신 결정적인 신호

포인터가 낸 클릭은 `detail >= 1` 이고, 키보드로 낸 클릭과 스크립트의
`.click()` 은 `detail === 0` 입니다.

```
const 포인터가낸것 = e.detail > 0;
clickOrigin = 포인터가낸것 ? { down: downAt || self, up: upAt || self }
                          : { down: self, up: self };
```

포인터가 낸 클릭이면 **바로 앞의 `pointerdown` 이 그 클릭의 것**이라
기록이 낡을 수가 없고, 아니면 애초에 기록을 안 봅니다. 그래서
`pointercancel`·`contextmenu` 리스너와 시간 창을 **셋 다 걷었습니다** —
같은 일을 여러 곳이 하면 한쪽만 고쳐집니다.

**점검에 느린 드래그를 넣었습니다.** `끌어보기` 가 이벤트를 한 틱에
몰아 쏘면 경과가 0ms 라 **언제나 초록**입니다 — 그 자리에 `뜸` 을 두어
2초를 끌어 봅니다.

### 그리고 점검이 `detail` 을 안 실어 보내고 있었습니다

고친 코드로 통째로 돌렸더니 **드래그 셋이 빨갰습니다.** 직접 재면
멀쩡한데 스크립트에서만 그랬습니다 — `끌어보기` 가 `MouseEvent` 를
`detail` 없이 만들어서 **0** 이 되고, 새 판정이 그것을 **키보드
클릭으로** 본 것입니다.

**재는 쪽이 실제와 달랐습니다.** 진짜 포인터 클릭은 `detail >= 1`
입니다. 실어 보내게 고치니 통과합니다 — `pointermove` 를 안 쏘던 것과
같은 갈래이고, **이번 판에서 두 번째**입니다.

그리고 **「우클릭 뒤 키보드 클릭」 항목은 그대로 둡니다** — 통과합니다.

## 5. [9][10] 점검 파일 — **여기서 셋이 더 드러났습니다**

### (9-가) `pointermove` 를 안 쏘고 있었습니다 — 그래서 1판의 확인이 근거가 못 됐습니다

옛 400ms 창은 `moved`(2px 넘게 움직였나)가 참일 때만 시각을 찍었습니다.
움직임을 안 쏘면 **무엇 때문에 빨개졌는지 갈립니다.**

`pointermove` 를 쏘게 하고 **옛 코드로 되돌려 다시 쟀습니다.**

| 항목 | 옛 코드 |
|---|---|
| 드로어 본문에서 눌러 여백에서 뗌 | **✗ 닫힘 — 이것이 이번 버그** |
| 폭 조절 핸들에서 눌러 여백에서 뗌 | **✓ 안 닫힘** |

**검토자의 의심이 맞았습니다.** 1판에서 핸들 항목이 빨갰던 것은
down/up 때문이 아니라 **`moved` 가 거짓이어서**였습니다. 움직임을 쏘니
옛 400ms 창이 제대로 막습니다.

그래서 **핸들 항목이 잡는 것은 이번 버그가 아니라 회귀**입니다 —
400ms 창을 걷어낸 자리를 down/up 이 정말 대신하는가. 그 사실을 주석에
적었습니다. **이번 버그를 잡는 것은 본문 항목입니다.**

### (9-나) 항목들이 서로에게 기대고 있었습니다

옛 코드로 처음 돌렸을 때 본문 항목이 빨개지자 **핸들 항목이 아예 목록에
없었습니다** — 이미 닫혀 있어 `if (열려 있으면)` 에 걸렸습니다.
**「무엇이 고장인지」 가 아니라 「무엇을 쟀는지」 가 사라집니다.**

`열어둔다()` 를 두어 각 항목이 필요하면 다시 열고, 못 열면 그 사실을
화면에 남깁니다.

### (9-다) 핸들 드래그가 **진짜로 폭을 바꿉니다**

움직임을 쏘게 되면서 생긴 것입니다. 그러면 처음에 찾아 둔 여백 좌표가
더 이상 여백이 아니라, 뒤 항목(①)이 **「고침이 과하다」 로 잘못
빨개졌습니다.** 실제로 한 번 그랬습니다.

폭을 되돌리고, ① 과 우클릭 항목은 **여백을 다시 찾아** 씁니다.

### (10) 빈 칸이 없으면 말없이 건너뛰었습니다

`if (empty) { … }` 뿐이라 아무 줄도 안 남았습니다 — **항목 수만 줄고
이유가 화면에 없습니다.** 「빈 칸이 없어 드래그 시험 다섯을 건너뜀」 을
남깁니다.

### 셋째 항목 라벨

「가장 흔한 드래그」 는 과했습니다. 둘 다 안이면 브라우저는 click 도
드로어 안에 내므로 **옛 코드에서도 안 닫히던 모양**입니다. `click` 을
드로어에 내도록 고치고 라벨을 **「원래 안 닫히던 모양 · 회귀 방어」** 로
바꿨습니다.

브라우저가 옛 파일을 물고 있을 수 없습니다.

### 손으로 눌러 본 것 — **운영 화면에서 확인했습니다**

**사용자가 운영 화면(`127.0.0.1:8000`)에서 직접 눌러 넷을 확인했습니다.**

> **누가 확인했는지 적어 둡니다.** 제가 운영 화면에 로그인하지
> 못했습니다 — 이 브라우저 프로필에 `httponly` 인 `dcb_session` 이
> 남아 있어 자바스크립트로 덮을 수 없고, 초대 링크를 재발급하면

> 않았습니다. 그래서 그 자리는 사용자가 대신 눌렀습니다.

## 이번에 걸린 것

1. **규칙을 새로 적으면서 그것을 대신하는 옛 규칙을 두 줄 위에 그대로
   두었습니다.** 11-3 3단계를 아예 안 했습니다 — 보고에 그 절 자체가
   없었습니다
2. **보고에 「하나도 없었다」 고 과장했고, 고치면서 숫자를 또 틀렸습니다.**
   없었던 것은 방향이 아니라 모양 하나인데 「하나도 없다」 고 썼고,
   그것을 고치며 **정의 줄까지 세고 옛 상태에 새 수를 달았습니다**
   (36/3 → 실제는 그때 34/1). **「없다」 고 쓰기 전에도, 「몇 개」 라고
   쓰기 전에도 세었어야 합니다**
3. **확인의 근거가 갈려 있었습니다.** `pointermove` 를 안 쏘아서, 옛
   코드에서 핸들 항목이 빨개진 것이 down/up 때문인지 `moved` 가
   거짓이어서인지 알 수 없었습니다. 쏘아 보니 **후자**였고, 그래서
   핸들 항목의 뜻이 「이 버그를 잡는다」 에서 「회귀를 막는다」 로
   바뀌었습니다
4. **시험 항목들이 서로에게 기댔습니다.** 앞이 실패하면 뒤엣것이
   말없이 안 돌아, 무엇을 쟀는지가 사라졌습니다
5. **시험이 화면을 실제로 바꾸는 것을 안 셌습니다.** 핸들 드래그가
   진짜로 폭을 바꿔서, 처음 찾아 둔 여백 좌표로 재던 뒤 항목이 잘못
   빨개졌습니다
