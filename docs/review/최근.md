# 4. 판단이 들어간 자리

1. **겹침이 나오면 아무것도 안 바꾼다**(`BEGIN` 뒤라 칸 붙임까지 되돌아간다) — 지시는 「만들지 말고 센다」 였는데 옮기기에서 겹치는 것은 새로 만드는 행이 아니라 이미 있는 run 이다. 그 run 을 안 옮기면 사라질 품목을 계속 가리켜(CASCADE 라 품목을 지우면 run 이 함께 사라진다) 데이터를 잃거나 새 유니크를 못 건다. 그래서 겹침이 하나라도 있으면 표를 그대로 두고 몇 건인지 말한 뒤 1 로 끝난다(예외 없음 · 사본은 떴음) — 사람이 그 줄을 정리한 뒤 다시 돌린다. 「비품옮기기.py 의 그 자리와 같은 모양」 은 세고 말하는 것이지 건너뛰는 것이 아니다.
2. **전부 SQL 로 했다** — 지시가 autoflush 를 잊지 말라 했는데, ORM 은 이미 새 모양이라 옛 칸(품목의 묶음)을 읽을 수 없다. 세션의 연결로 SQL 을 실행하고 `create_all(bind=그 연결)` 로 새 표를 세운다. **「한 트랜잭션」 은 처음엔 거짓이었다** — pysqlite 는 DML 앞에서만 BEGIN 을 내므로 첫 ALTER 가 밖에서 혼자 커밋됐다(검토가 임시 DB 로 재서 잡음). 이제 첫 문장이 `BEGIN` 이고 `test29_c05` 가 표를 세우다 죽게 해 ALTER 까지 되돌아가는 것을 잰다. 중간에 죽으면 남는 것은 없다 — 저널이 전부 되돌린다. 겹침은 임시 표(`_eq_map`)와 GROUP BY 로 센다 — flush 문제가 애초에 없다.
3. **표를 다시 세우는 순서** — SQLite 는 유니크를 그 자리에서 못 걷는다. 이름 붙은 인덱스 셋을 먼저 걷고(새 표가 같은 이름을 쓴다) 옛 표를 `_old` 로 이름을 바꾼 뒤 `create_all` 로 새 표를 세우고 `INSERT … SELECT` 로 옮겨 담고 옛 표를 지운다. FK 를 켠 채로도 된다 — RENAME 이 참조를 따라 바꾸고, 옛 표는 자식(run)부터 지운다. `foreign_key_check` 가 비지 않으면 되돌리고 예외.
4. **부팅은 말만 한다** — 지시대로 스스로 고치지 않는다. `_ADDED_COLUMNS` 에 `group_name` 을 넣지 않은 것도 그 때문이다(칸만 붙이면 반쯤 옮긴 표가 되고 품목의 묶음 칸·옛 유니크는 남는다). 옛 모양인 채 새 코드로 뜨면 `/equipment` 가 500 이 아니라 「아직 못 읽습니다」 를 낸다(검토 뒤 — 500 은 놓친 사람에게 아무 말도 안 한다). **창은 어느 순서든 비품 화면 하나뿐이다**: 스크립트를 먼저 돌리면 옛 코드가 도는 동안 옛 ORM 이 품목의 묶음을 읽으려다 `/equipment` 가 실패하고, 재시작을 먼저 하면 스크립트까지 「아직 못 읽습니다」 다. 다른 화면은 그 표를 안 읽는다. 이번 판은 재시작이 먼저다(4장 6) — 그 창의 화면이 500 보다 말이 되게.
