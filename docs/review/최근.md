## 8번 — 회의 하나에 드는 값 (**추정**)

부른 적이 없으므로 곱셈만 적습니다. **화면에는 실제 값이 뜹니다** —
`llm.대답.원` 이 응답의 `usage` 를 그대로 쓰기 때문입니다.

```
1차 입력 = 시스템 896자 + 목록 6,312자 + 회의록 1,431자 + 틀 181자 ≈ 8,900자
글자당 0.6~0.75 토큰으로 보면 5,340~6,675 토큰

입력 $3/MTok · 출력 700토큰 $15/MTok → $0.027~0.031 ≈ 37~43원
2차까지 부르면 대략 두 배 — 회의 하나에 **40~90원**
```

**모델은 Sonnet 이 기본입니다** (`DCB_LLM_MODEL` 로 바꿉니다). 회의록을
저장할 때마다 자동으로 부르고 회차마다 50건쯤이라 값이 성능만큼 중요한데,
이번에 넘어야 할 벽("그 얘기를 한 적이 없다" 를 알아보는 것)은 Sonnet 이
합니다.

**요금표는 바뀝니다.** `llm.PRICE_IN`·`PRICE_OUT` 한 곳에 있고 문서(14-5)가
같이 가리킵니다 — 안 고치면 **화면의 값만 틀립니다.**

## 7번 — 2차를 언제 부르나

> *1차가 논의 후보를 냈고, **그중 논의 이력이 있는 업무가 하나라도 있을 때.***

이력이 없으면 2차가 볼 것이 없어서 같은 것을 한 번 더 묻는 것이 되고 값만
두 배가 됩니다. **안 부른 이유도 화면에 적습니다** — `2차: 후보 업무에 지난
논의가 없어 볼 것이 없습니다`. 조용히 안 부르면 나중에 "2차가 도는 게 맞나"
를 코드를 읽어야 알게 됩니다.

## 15번 — API 가 죽으면 (그리고 **왜 그렇게 했나**)

**낱말 겹침으로 물러서고, 물러섰다고 화면에 적습니다.** 빈 목록으로 두지
않았습니다.

빈 목록은 이미 다른 뜻을 갖고 있습니다 — **"할 말이 없다"** (4-10 조건 4의
정상, 50건 중 24건이 그렇습니다). 실패를 같은 모양으로 내면 **둘이 구별되지
않고, 구별되지 않는 실패가 이 프로젝트에서 가장 비쌉니다.**

그래서 `state` 를 셋으로 나눴습니다 — **도는중 / 됨 / 실패.** 사람이 할 일이
전부 다릅니다: 기다린다 / 읽는다 / 다시 누른다.

**실패는 저절로 다시 돌리지 않습니다.** 화면이 3초마다 물어보는데, 실패까지
자동 재시도로 두면 죽은 API 를 계속 두드리며 값만 나갑니다. 다시 시도는
사람이 누릅니다 (18번).

**오류 본문을 화면에 그대로 붙이지 않습니다.** 오류 본문에 키가 되비쳐 오는
일이 있고 이 말은 화면에 뜹니다 — 상태 코드와 종류까지만 옮깁니다
(`test_llm_15b`).

## 20번 — 사람 평가를 어떻게 막았나

**보내는 것은 막지 않았습니다** (지시대로). 다만 **제안에 인용돼 들어가면
논의로 남고, 그러면 회차를 볼 수 있는 누구나 보게 됩니다** (4-9).
그래서 **두 겹**으로 막습니다.

1. **프롬프트** — "사람에 대한 평가는 인용하지도 요약하지도 마세요"
2. **나온 것을 다시 거릅니다** (`사람평가_섞였나`) — 프롬프트로만 막으면
   안 지켜졌을 때 **아무 표시가 없습니다**

거르는 방법을 한 번 고쳤습니다. 처음에는 **줄 통째로** 견줬는데 못 잡았습니다 —
실제로 걸린 것은 `정하윤은 체력 약함이라 스트랩 발주를 맡깁니다` 처럼
**한 조각만 옮겨 붙은 것**이었습니다.

그렇다고 아무 조각이나 막으면 `정하윤` 같은 이름까지 막혀 **담당을 적는
정상적인 문장이 함께 지워집니다.** 그래서 조건을 둘 다 겁니다 —
**네 글자 이상**이고, **평가로 읽히게 만든 그 말**(`약함`·`잘함`·MBTI …)을
실제로 품고 있을 것. 그 말이 없으면 그 조각은 평가가 아니라 그냥 사실입니다.

결정사항은 **인용이 본체**라 평가가 섞이면 통째로 뺍니다. 논의는 근거만
갈아 끼웁니다.

화면에도 뜹니다 (브라우저에서 읽은 그대로) —

```
이 회의록에는 사람에 대한 평가로 보이는 대목이 8줄 있습니다 (9장).
제안에는 그 대목을 담지 않습니다.
      배경 rgb(250,241,210) · 글자 rgb(55,53,47)
```

> **`--warn` 을 글자색으로 쓰지 않았습니다.** `--span` 위에서 4.14:1 이라
> 9장의 4.5:1 을 못 넘깁니다(혼자 뜻을 지는 글자입니다). 잉크로 쓰고 색은
> **왼쪽 마개**에만 뒀습니다 — 색을 아끼는 4-0 과도 같은 방향입니다.

## 판단이 들어간 자리

### ① 낱말 겹침을 지우지 않았다

성적표가 "여기까지" 라고 결론지은 방식인데 남겼습니다. **갈 자리가 필요하기
때문**입니다 — 키가 없거나 API 가 죽었을 때. 빈 목록으로 두면 정상과
구별되지 않습니다. 대신 **물러섰다고 화면에 적습니다.**

### ② 상태를 담되 그날로 되돌린다

전에는 상태를 아예 안 담았습니다("담으면 본다"). 문장으로 읽으려면 필요한데,
저장된 `status` 는 **오늘의 값**입니다. 그래서 `started_at`·`completed_at`
**날짜에서 다시 계산**합니다 — 4-10 이 기한 초과를 저장된 '지연' 이 아니라
날짜로 계산하기로 한 것과 같은 자리입니다.

### ③ 사람 평가를 조각으로 막되, 이름은 안 막는다

위 20번에 근거를 적었습니다. **네 글자 이상 + 평가말을 품은 조각**만
막습니다. 더 넓게 막으면 담당을 적는 정상적인 문장이 함께 지워집니다.

### ④ 결과를 회의록 행에 쌓는다 (새 표를 안 만들었다)

`meetings` 에 컬럼 여섯을 더했습니다(`_ADDED_COLUMNS`). 1:1 이라 표를 새로
만들 이유가 없고, 이 프로젝트의 스키마 변경은 **추가만** 합니다 (14장).

### ⑤ Sonnet 을 기본으로 뒀다

회의록을 저장할 때마다 자동으로 부르고 회차마다 50건쯤이라 값이 성능만큼
중요합니다. 이번에 넘어야 할 벽은 Sonnet 이 합니다. 더 어려운 것을 시키려면
`DCB_LLM_MODEL` 로 바꾸되 **요금도 함께** 바꿔야 합니다.

### ⑥ 도는 중을 3초마다 다시 물어본다

끝나면 **저절로 나타나야** 합니다 — 사람이 새로고침해야 보이면 아무도
안 기다립니다. 다만 **실패는 다시 안 돌립니다** (위 15번).
