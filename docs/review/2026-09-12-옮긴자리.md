# 2. 옮긴 사실을 무엇으로 남겼나 (지시 1-b) — **날짜가 아니라 며칠**

지시가 둘 중 하나를 고르라고 했습니다. **「그때 셈한 자리에서 며칠」** 을
골랐습니다(`TaskRun.moved_offset_days`).

**날짜를 두면 개회일이 바뀔 때 며칠 밀렸던 것인지를 다시 알아내야 하는데,
그러려면 옛 개회일이 있어야 합니다.** `reschedule(db, retreat)` 은 그것을
안 받습니다 — 부르는 자리가 이미 `retreat` 에 새 날짜를 넣고 `db.commit()`
을 한 뒤에 부릅니다. 옛 개회일을 인자로 더해 넘길 수는 있지만, 그러면
**날짜를 정하는 데 필요한 값이 함수 밖에 하나 더 생깁니다** — 그 자리를
안 지나는 길(스크립트 · 다음에 생길 화면)이 옛 개회일을 안 줄 때 조용히
틀립니다.

**며칠인지를 두면 새 개회일에서 셈한 자리에 그대로 더하면 됩니다.** 옛
개회일이 필요 없고, 함수가 받는 것만으로 답이 나옵니다.

| 어디 | 무엇 |
|---|---|
| `TaskRun.moved_offset_days` | 셈한 자리에서 며칠. NULL 이면 안 옮긴 것. **0 도 값입니다**(기본 자리로 끌어다 놓은 것) |
| `TaskRun.moved_at` | 그 자리를 정한 때. **비면 지금은 안 따르는 것**이고 위 값은 남습니다 |
| `TaskLibrary.dates_changed_at` | 상대 위치 네 값을 마지막으로 고친 때 |

**기간(길이)은 run 이 지금 가진 길이를 지킵니다.** 드로어에서 마감일만
고치는 것도 같은 엔드포인트(`/dates`)로 들어오므로, 라이브러리 길이로
되돌리면 **늘려 둔 기간이 조용히 사라집니다.** 그래서 마감일만 고쳐도
「사람이 정한 자리」 로 남깁니다(그때 며칠은 0 입니다).

## 2-1. 물러선 쪽을 안 지웁니다 (지시 1-c)

**어느 쪽도 지울 필요가 없습니다.** 옮긴 값은 칸에 그대로 있고 라이브러리
자리는 언제든 다시 셀 수 있으므로, **오가는 것은 `moved_at` 하나**입니다.

- 옮긴 자리로 → `moved_at` 을 지금으로 (라이브러리가 나중에 바뀌었던 것보다 뒤가 됩니다)
- 라이브러리 자리로 → `moved_at` 을 비움 (`moved_offset_days` 는 남습니다)

## 2-2. 부팅은 칸을 붙이기만 합니다 (지시 1-d)

`_ADDED_COLUMNS` 에 셋을 더했고 **값을 채우지 않습니다.** 이미 선 업무는
NULL 이라 「안 옮김」 으로 시작합니다.

**채울 수도 있었습니다** — 지금 날짜가 라이브러리 셈과 다른 run 을 찾으면
됩니다. **안 했습니다**: 그 차이가 「사람이 옮긴 것」 이라는 보장이 없습니다.
라이브러리를 나중에 고쳤어도 똑같이 다릅니다. 지어낸 기록을 심지 않습니다(6-9).

**운영에서 그런 run 이 몇인지는 세었습니다** — 5장에.

# 3. 개회일이 바뀔 때 (지시 2)

`library._plan` 이 run 마다 셋 중 하나로 가릅니다.

| 무엇이 | 어떻게 | 지시 |
|---|---|---|
| 안 옮긴 업무 | 라이브러리에서 **다시 셉니다** — 전과 같습니다 | 2-a |
| 옮긴 업무 | **같은 간격만큼 함께 밉니다** | 2-b |
| 켠 채 날짜가 빈 업무 | **빈 채로 둡니다** | 2-c |

## 3-1. AW-c 를 `dweek` 이 아니라 `reschedule` 에서 닫았습니다 (지시 2-c)

AW-c 는 `dweek.resolve_dates` 의 `d_week or FIRST_D_WEEK` 를 가리키고
있었습니다. **그 줄을 안 고쳤습니다.**

그 함수는 **마법사도 씁니다.** 거기서는 D-주차가 비었을 때 기본 자리로
떨어뜨리는 것이 맞습니다 — 업무를 **어디에 놓을지 정하는 중**이기 때문입니다.
고장은 그것이 아니라 **「이미 비어 있는 것을 채우는 것」** 이고, 비어 있는지
아는 자리는 `reschedule` 입니다. 그래서 거기서 막았습니다.

AW-c 가 「`dweek` 의 그 한 줄만 고치면 넓은 쪽이 그대로 남습니다」 라고 적어
둔 것과 같은 결론입니다 — **넓은 쪽(켠 run 의 날짜가 비어 있으면)에서
막았습니다.**

## 3-2. 저장하기 전에 세 수 (지시 2-d)

개회일 칸을 고치면 그 자리에서 뜹니다. **수를 코드에 박지 않습니다** —
`library.reschedule_preview` 가 그때 자료를 셉니다.

**보여 주는 쪽과 실제로 옮기는 쪽이 같은 `_plan` 을 씁니다.** 두 곳에서
따로 세면 보여준 수와 실제가 갈리고, 갈린 쪽을 아무도 눈치채지 못합니다.

개발 서버에서 실제로 재었습니다(회차 1 · 2026-08-21 → 2026-09-04):

```
저장하면 — 다시 셀 업무 95건 · 손으로 옮긴 자리 그대로 밀 업무 1건 · 날짜가 빈 채 남을 업무 0건
```

그 1건이 **바로 앞에서 사흘 미뤄 둔 업무**입니다. 같은 개회일이면
`{"changed": false}` 라 아무 줄도 안 뜹니다.

## 6-1. 그동안 운영이 어떤 상태인가 — **어긋나 있지 않습니다**

돌고 있는 프로세스는 **옛 코드 전부**입니다(켤 때 읽은 것을 들고 있습니다 —
11-2). 그 코드는 새 칸을 모르고, 운영 DB 에도 그 칸이 없습니다. 읽어서
확인했습니다:

```

task_runs 에 moved_at: False
task_library 에 dates_changed_at: False
```

**「새 화면 + 옛 코드」 가 아니라 「옛 코드 + 옛 DB」 입니다.** 11-2 가
경고한 그 조합과 다릅니다 — 지금은 아무것도 안 어긋나 있고, **재시작하는
순간 칸이 붙습니다**(부팅의 `_catch_up_columns`).

**그 창이 시험 하나를 건드립니다.** `test_y_13f` 는 운영 DB 를 직접 읽는데,
모델이 아는 칸이 그 파일에 없어 빨개졌습니다 — **고장이 아닌데 빨간
자리**입니다. 그때는 건너뛰고 왜인지 적게 했습니다(8장). **고치는 길은
시험이 아니라 재시작이고**, 재시작한 뒤에는 다시 통과합니다.
